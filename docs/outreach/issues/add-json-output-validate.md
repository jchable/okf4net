### Title: Add a `--json` machine-readable output option to `okf validate`
**Labels:** help wanted ; enhancement
**Difficulty / est. effort:** ~half day, medium

**Context:** `ROADMAP.md`'s "Next" section explicitly calls for "CLI ergonomics: richer diagnostics and machine-readable (`--json`) output where it aids tooling." `okf validate` (§9 conformance) is the natural first candidate: today it only emits human-readable lines via `Diagnostic.ToString()` (`[severity] path: message`, see `src/OKF4net/Validate.cs`), which is awkward for CI tooling to parse reliably. `BundleValidator.Validate` already returns a fully structured `ValidationReport` (`Diagnostics`, `IsConformant`, `ErrorCount`, `WarningCount`) — the CLI layer just needs a serialization path.
**Files to touch:** `src/OKF4net.Cli/OkfCli.cs` (`CmdValidate`, `Usage` constant), `tests/OKF4net.Tests/CliTests.cs`, `README.md`
**What to do:**
1. In `src/OKF4net.Cli/OkfCli.cs`, add a `--json` flag check (reuse the existing `HasFlag` helper, same pattern as `graph`'s `--dot`) inside `CmdValidate`.
2. When `--json` is set, emit a JSON document instead of the current text format: an array of diagnostics (each with `severity`, `path`, `concept`, `message` — pulling directly from the `Diagnostic` record's fields, `src/OKF4net/Validate.cs`) plus a summary object (`concept_count`, `error_count`, `warning_count`, `info_count`, `conformant`, `okf_version`). Since the CLI is Native AOT-published (`PublishAot`, see `Directory.Build.props`/the CLI csproj), prefer hand-rolled JSON string building (escaping strings the same way `RustDebugQuote`/the YAML emitter already hand-roll quoting elsewhere in this codebase) over `System.Text.Json`'s reflection-based serializer, to avoid AOT trimming warnings — or use `System.Text.Json` with a source-generated `JsonSerializerContext` if you prefer; either way it must build clean under `dotnet publish src/OKF4net.Cli -c Release`.
3. Keep the exit code semantics identical to the existing text mode (`0` if conformant, `1` otherwise).
4. Update the `Usage` constant to mention `--json` under `OPTIONS:` (or scoped to the `validate` line), and add a short example to the README's `### As a CLI` section.
5. Add tests in `tests/OKF4net.Tests/CliTests.cs` covering both a conformant and a non-conformant bundle in `--json` mode, asserting the output parses as valid JSON (e.g. via `System.Text.Json.JsonDocument.Parse` in the test, which has no AOT constraint since tests run on the full runtime) and contains the expected fields.
**How to verify:** `dotnet test OKF4net.sln --filter "FullyQualifiedName~CliTests"`, plus `dotnet publish src/OKF4net.Cli -c Release` to confirm the AOT publish still succeeds (this is also checked in CI's `ci.yml`).
**Good to know:** No new third-party dependency is allowed in `src/OKF4net.Cli` (BCL only, per `CLAUDE.md`'s Hard rules) — `System.Text.Json` is part of the shared framework, not a third-party package, so it's fine, but AOT-safety (source-generated context, no reflection-based `JsonSerializer.Serialize<object>` calls) must be verified. See `CONTRIBUTING.md` for the build/test/format loop.
